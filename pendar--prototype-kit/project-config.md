# CLAUDE.md

This is the **Prototype Kit** — a starter template for designers to rapidly build, share, and deploy interactive prototypes using Claude Code. Prototypes here are standalone HTML explorations deployed to GitHub Pages.

## Architecture

```
/
├── index.html                  # Main viewer (search, list, pagination)
├── prototypes.json             # Auto-generated manifest (DO NOT edit manually)
├── generate-manifest.sh        # Local manifest generation
├── shared/
│   ├── prototype-chrome.js     # Shared header/navigation component
│   ├── prototype-chrome.css    # Chrome styles
│   ├── comments.js             # Spatial commenting (GitHub Issues backend, optional)
│   └── comments.css            # Comment UI styles
├── .claude/
│   └── skills/
│       ├── design-brainstorm/  # Design crit + brainstorm partner
│       ├── ux-writing/         # UX writing review
│       └── match-design/       # Visual iteration loop
├── _sample-prototype/          # Deletable example (see pattern below)
│   ├── index.html
│   ├── meta.json
│   ├── hello-world.html
│   └── dark-card.html
└── <prototype-folder>/
    ├── index.html              # Chrome wrapper (see template below)
    ├── meta.json               # Name, description, tags, iterations, options
    ├── thumbnail.png           # Optional — shown in the viewer list (64x48)
    ├── option-1.html           # Prototype content pages (loaded in iframe)
    ├── option-2.html
    └── ...
```

- **`prototypes.json`** is generated by `./generate-manifest.sh` and committed to the repo. Regenerate it before pushing whenever you add, remove, or modify a prototype.
- **`index.html`** (root) is the viewer — pure static HTML/CSS/JS. Fetches `prototypes.json` at runtime.
- **Shared chrome** (`/shared/`) renders a consistent header across all prototypes with iteration and option navigation.
- **`_sample-prototype/`** is an example showing the file structure. Delete it once you understand the pattern.

## Styling Prototypes

This kit is **unopinionated about styling** — it ships no component library and no design tokens. Build UI with plain, semantic HTML and CSS, and bring whatever styling approach you prefer:

- Write a `<style>` block inside each option file (simplest for one-off explorations).
- Or drop your own stylesheet / design-system CSS into `shared/` and link it from your option files with a relative path.
- Or pull in any CDN framework you like via a `<link>` / `<script>` tag.

Keep each option file self-contained where practical — it's a standalone HTML document loaded in an iframe. If you have a design system with design tokens, prefer referencing its tokens (as CSS custom properties or your own variables) over hardcoding colors and spacing, so light/dark and rebranding stay easy.

## Matching a Visual Reference

**When the user provides a Figma link or a screenshot/image as a reference for a prototype, you MUST close the loop visually** — don't just build once and assume it matches. Build, screenshot the running prototype, compare it against the reference, refine, and repeat until a human would perceive the two as the same design.

**This loop is conditional:**
- **Visual reference provided** (Figma URL or screenshot/image) → run the visual iteration loop.
- **No visual reference** (the prototype is built from a text description alone) → there is nothing to diff against, so skip the loop and build normally.

The goal is human-perceived equivalence, **not** pixel-perfection. The implementation is usually responsive while a Figma frame is fixed-width, so exact dimensions will differ — that's fine. Ask "would a designer call this the same design?", not "do these overlap pixel-for-pixel?"

The full step-by-step procedure lives in the **`/match-design`** skill (serve → screenshot the bare option file → compare against a rubric → refine → repeat, max 4 iterations, then report honestly including any remaining discrepancies). Follow that skill whenever this trigger fires. The skill can also be invoked on demand to match an already-built prototype against a reference.

## Skills

- **`/design-brainstorm`** — Design crit and brainstorm partner grounded in durable product-design principles (reduce cognitive load, design for the whole context, prototype to learn, focus effort where it pays off, make bold bets)
- **`/ux-writing`** — UX writing review and recommendations. Evaluates copy against content-design principles, a tone-by-context framework, and litmus tests. Use when writing or reviewing any user-facing text.
- **`/match-design`** — Visual iteration loop: screenshots the running prototype, compares it against a Figma link or reference screenshot, and refines until a human would perceive them as the same design. Auto-triggered when a visual reference is provided (see "Matching a Visual Reference" above); also invokable on demand.

## MCP Servers (optional)

- **Figma Plugin** — reads Figma designs for design-to-code workflows. Install with `claude plugin install figma@claude-plugins-official`, then authenticate on first use. Not required, but recommended for the Figma-to-prototype workflow.
