# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Rust terminal (ratatui) AI language tutor. Exercises, curriculum, and answer analysis are generated by an LLM provider the user configures (OpenAI, Anthropic, Google, DeepSeek, Mistral, OpenRouter, Ollama, or a custom OpenAI-compatible endpoint via `rig-core`). Data is stored locally per language pair in LanceDB tables under `.open-course-cli/`, and can optionally sync to the cloud (see Sync below).

Read `README.md` for install/usage and `docs/flow.md` for the full user-facing flow (onboarding, dashboard, session lifecycle, settings, account/sync) — both are kept current and are the source of truth for behavior, not just this file.

## Commands

```bash
cargo run -p open-course-cli                     # run the TUI (data in ./.open-course-cli/)
cargo run -p open-course-cli -- --data-dir /path # run against a different data dir
cargo test --all-features                        # run all tests (workspace)
cargo test -p open-course-cli --test session_test # run a single test file
cargo test some_test_name                        # run a single test by name
cargo clippy --all-targets --all-features -- -D warnings  # lint (mirrors CI)
cargo fmt --all                                  # format (mirrors CI)
python3 scripts/debug_exercises.py               # debug LLM exercise generation directly
```

Set `OPEN_COURSE_CLI_DEBUG=1` to enable debug event logging (see `crates/llm/src/debug_log.rs`, `crates/llm/src/pipeline.rs::log_debug_event`).

## Workspace layout

The repository is a Cargo workspace with a one-directional dependency graph:

```
core ← {config, db}
{core, config} ← llm
{core, db} ← sync
{core, db, llm, config} ← service
{core, db, llm, config, service, sync} ← cli
```

- `crates/core` (`open-course-core`) — pure domain: types (`Topic`, `ProgressTopic`, `SessionSummary`, `LearningItem`, all with `updated_at`/`deleted_at` for sync), session orchestration, scoring, dashboard stats, `AppError`/`Result`. No DB, no UI.
- `crates/db` (`open-course-db`) — LanceDB tables, Arrow converters, `Database`, the schema-migration registry, and the sync outbox.
- `crates/config` (`open-course-config`) — `OpenCourseConfig`, profiles, providers, on-disk config migrations.
- `crates/llm` (`open-course-llm`) — LLM clients, prompts, parsing, retry/streaming, diagnostics; also owns the `LlmResult` enum (moved here from the app to break the app↔llm cycle).
- `crates/service` (`open-course-service`) — the service layer: business logic shared between the CLI and any future frontend (e.g. an HTTP server).
- `crates/sync` (`open-course-sync`) — cloud sync client: defines the wire protocol the future server must implement, plus the token store.
- `crates/cli` (`open-course-cli`) — the `opencourse` binary: event loop, views, widgets — a thin adapter over `service` and `sync`.

### Event loop and state (`crates/cli/src/app/mod.rs`)

Single-threaded async event loop in `run_app`. One `AppState` struct holds the current `View` enum plus one state struct per view (`DashboardState`, `SessionState`, `CurriculumState`, etc. — all in `crates/cli/src/ui/views/`). Each loop iteration:

1. Draws the current view (`draw()` matches on `state.view`).
2. Kicks off pending background work (e.g. auto-loading session topics/curriculum when a view needs them but has none loaded).
3. `tokio::select!`s over four sources: terminal input (`EventStream`), an `mpsc::Receiver<LlmResult>` for async LLM responses, an `mpsc::Receiver<SyncMessage>` for async sync/account work, and a 100ms tick (only redraws when a view is actively waiting — `redraw_on_tick`).

Key/mouse handling dispatches to a per-view module (`dashboard::handle_key`, `session::handle_key`, etc. in `crates/cli/src/ui/views/`), which mutate `AppState` directly and return `Result<()>`.

Two background-result channels exist side by side:

- **LLM**: tasks send an `LlmResult` variant (`Exercises`, `Analysis`, `Curriculum`, streaming chunks, diagnostics, ...) through `llm_tx`; `app/llm_results.rs::apply_llm_result` applies them — the single place async LLM results reach `AppState`. Add new LLM-backed features there.
- **Sync/account**: tasks send a `SyncMessage` variant (`DeviceFlowStarted`, `LoginFinished`, `BindScenarioLoaded`, `SyncFinished`, `CurriculumConflict`, ...) through `sync_tx`; `ui/views/settings/account.rs::apply_sync_message` applies them. Add new async sync features there rather than blocking the event loop.

### Views (`crates/cli/src/ui/views/`)

Each view is a module exposing `draw()` and `handle_key()` plus a `*State` struct owned by `AppState`. Views: `onboarding` (multi-step wizard, own `state.rs`/`steps.rs`/`handlers.rs` submodules), `dashboard`, `session`, `docs`, `report`, `curriculum`, `settings` (own `fields.rs`/`data.rs`/`provider_setup.rs`/`account.rs` submodules), `model_check`, `pairs`, `update`. Shared widgets (activity calendar, sparkline, progress bars, spinner, markdown rendering) live in `crates/cli/src/ui/widgets/`.

Mouse wheel scrolling is only enabled on views without text input (`view_supports_mouse`); `m` toggles mouse capture off for native text selection.
