# CSV Editor — コーディングエージェント作業規約

> このファイルはプロジェクト `CSV Editor` 専用の作業規約です。
> Claude Code / OpenAI Codex / Google Antigravity のいずれもこれを読みます。
> Home 全体のルール `/home/popos/AGENTS.md` も併せて適用されます（矛盾する場合は本ファイルが優先）。

## 0. ミッション

CSV を Excel に近い操作感で編集できる VS Code 拡張を作る。

参照ドキュメント（読む順）:

1. `docs/requirements.md` — 要件定義。要件ID (`CSV-FMT-011` 等) で参照する
2. **`docs/limitations.md` — 仕様上の制限事項。要件定義と矛盾する場合はこちらが優先。**
3. `docs/development-plan.md` — アーキテクチャ決定 (ADR)、フェーズ計画、各フェーズの完了条件
4. `docs/backlog.md` — 今回のスコープ外にした要件と復活条件
5. `docs/decisions.md` — 実装中に自分で下した判断の記録（**あなたが追記する**）
6. `docs/open-questions.md` — 判断できずに保留した論点（**あなたが追記する**）

**要件定義には、今回実装しないと決めた項目が残っている。** 大容量対応（§17）と文字コードの
自前制御（CSV-FMT-030〜033）が代表。`limitations.md` を必ず先に読み、
**スコープ外の要件を善意で実装し始めないこと。**

---

## 1. 絶対に破ってはいけない不変条件

要件 §25 の原則。**これに反する実装は、動いていてもバグとして扱う。**

1. **読み込み時に値を型変換しない。** `00123` は `123` にしない。`2026-01` を日付にしない。`1E10` を数値にしない。全セルは文字列
2. **編集していないセルのテキストを変更しない。** 1セルの編集は、そのセルのソース範囲内だけを
   書き換えること。ファイル全体の再シリアライズは**禁止**（`limitations.md` L-5）
3. **不正な CSV を黙って補正しない。** 検出して報告し、どうするかは利用者に選ばせる
4. **1つの論理操作 = 1つの `WorkspaceEdit`。** 複数セル入力・貼り付け・複数行削除・全置換は、
   まとめて1回の `WorkspaceEdit` にする。これが VS Code の Undo 1回に対応する（CSV-HIST-003）
5. **表示上の省略と実データの省略を混同しない。** 画面で `...` になっても値は完全に保持する
6. **フィルターによる非表示とデータ削除を混同しない。** 非表示行も保存対象
7. **部分失敗を許さない。** 貼り付け・一括置換が途中で失敗したら、操作前の状態へ戻す
8. **ログにセル値を出力しない。** 個人情報・機密情報が含まれうる。行番号と種別までに留める
9. **データの流れを一方通行に保つ。** 操作 → `TextEdit[]` を計算 → `WorkspaceEdit` を適用 →
   `onDidChangeTextDocument` → 再パース → 再描画。**テーブルを直接書き換えて画面を更新する近道を作らない**
   （開発計画 ADR-2）

この 9 項目は各フェーズの完了時に自己点検すること。

## 2. 進め方

### 2.1 フェーズ単位で進む

`docs/development-plan.md` §4 の M0 → M1 → ... の順に進む。

- **完了条件を全て満たすまで次のフェーズに進まない。** 満たせない項目があれば、そこで止めて報告する
- フェーズをまたいだ「ついでの実装」をしない。M2 の作業中に M4 の検索機能を書き始めない
- 1フェーズ完了ごとにコミットを分け、完了条件の充足状況を報告する
- **着手前に、完了条件が「やること」を覆っているか照合する。**
  覆っていない項目があれば、実装を始める前に指摘すること。
  完了条件は私（ユーザー）が書いており、漏れることがある。実例として M4 は
  「やること」に検索UIがあったのに完了条件がエンジン層だけで構成されており、
  UI が無いまま次フェーズへ進んでしまった。
  とくに「UI」「画面」「表示」に類する項目は、ロジック層のテストだけでは満たされない

### 2.2 M1 を飛ばさない

**UI が無い状態で CSV のパーサとシリアライザを完成させること。**
画面が見えないと進捗が実感しにくいが、ここが本プロジェクトの中心であり、
後から作り替えると全機能に波及する。焦って M2 に進まない。

とくに**パーサが返すセル単位のソース範囲（`start` / `end` / `quoted`）**は、
本アーキテクチャの全体がその上に乗っている。ここが不正確だと編集が壊れる。

### 2.3 M0 の実測を省略しない

M0 には「VS Code が実際に開けるファイルサイズ」「`@vscode/test-electron` が動くか」の
**実測**が完了条件に入っている。これは後続フェーズの前提を確定させるためのもので、
推測で埋めてはいけない。実測結果は `limitations.md` と `decisions.md` に必ず記録すること。

### 2.4 テストは実装と同時に書く

- 純粋関数（`parser` / `serializer` / `encoding` / `layout` / `selection` / `matcher` / `commands`）は**ユニットテスト必須**
- **テスト名の先頭に要件IDを入れる**。例:
  ```ts
  it('CSV-FMT-011: 引用符内のカンマを列区切りとして扱わない', () => { ... })
  ```
  これにより `grep -r "CSV-FMT-011" test/` で実装状況を機械的に確認できる
- 受け入れ条件 AC-001〜AC-012 は `test/acceptance/AC-001.test.ts` のように1ファイル1条件で作る
- **ラウンドトリップテスト（読んで書いてバイト一致）は常に緑に保つ。** これが壊れたら他を止めて直す

**テストを書く前に 8章「テストの誠実性」を必ず読むこと。**
緑になったことではなく、**壊したときに赤くなること**がテストの価値です。

## 3. 判断に迷ったとき

**仕様が決まっていない部分を勝手に決めて実装しない。** 以下の手順を取る。

1. `docs/requirements.md` と `docs/development-plan.md` を読み返す。§1 の決定表に答えがあることが多い
2. それでも決まらない場合:
   - **実装をブロックしない些細な選択**（変数名、内部データ構造、エラーメッセージの言い回し）… 自分で決めて `docs/decisions.md` に1行残す
   - **仕様に関わる選択**（利用者から見た挙動が変わる、要件の解釈が割れる、後から変えると手戻りが大きい）…
     `docs/open-questions.md` に「論点 / 選択肢 / 自分の推奨 / 保留中の影響範囲」を書き、
     **推奨案で仮実装して先に進み、その箇所に `// TODO(open-question): <見出し>` を残す**
3. フェーズ完了報告時に `docs/open-questions.md` の未解決分を必ず列挙する

止まって待つのではなく、仮決めして進み、判断の所在を記録に残すこと。

## 4. コード規約

- **TypeScript strict モード。** `any` を使わない。やむを得ない場合は理由をコメントに書く
- **コードコメントは日本語。** 識別子・型名・ファイル名は英語
- **UI 文言と利用者向けメッセージは i18n 経由。既定は英語 (en)、日本語 (ja) を用意する。**
  対象は Webview の全 UI 文言と、拡張側の通知・警告（サイズ上限の案内、文字コード警告、
  CR 保存警告など）。**リテラルの直書きをしない**。
  ロケールは `vscode.env.language` に従う。
  （2026-08-02 変更。当初は「UI 文言も日本語」としていたが、実機確認を受けて i18n 前提に改めた）
- **純粋関数と副作用を分ける。** `layout.ts` / `selection.ts` / `parser.ts` 等は
  VS Code API にも DOM にも Canvas にも依存させない。これはテスト容易性のための設計であり、崩さない
- **ホスト↔Webview のメッセージ型は `src/shared/protocol.ts` の1箇所に置き、両側が import する。**
  片側だけ型を書き換えない
- コメントは「何をしているか」ではなく**「なぜそうしたか」**を書く。特に CSV の仕様上の例外処理には理由を必ず添える

### 依存パッケージ

- **追加は最小限。** 追加する場合はコミットメッセージに理由を書く
- 使用が確定しているもの: `vitest`（テスト）、`fast-check`（プロパティテスト）、`esbuild`（バンドル）
- **CSV パーサのライブラリは使わない。** 理由は development-plan の ADR-3。
  既製パーサ（papaparse / csv-parse）が**セル単位のソース位置を返さない**ためであって、
  エスケープ方式への対応が理由ではない（それらは `escapeChar` / `escape` で対応できる）。
  「バックスラッシュエスケープのために自作が必要」という説明を見かけたら、それは誤りなので従わないこと
- **文字コード変換ライブラリ（`iconv-lite` 等）は入れない。** 変換は行わない（`limitations.md` L-2）。
  検出のみ行うが、それも自前の軽量判定で足りる
- グリッドUIのライブラリ（ag-grid、Handsontable 等）**も使わない**。ライセンスと、要件が求める細かい挙動の制御が効かないため

## 5. 環境固有の注意

- **`sudo` は使えない。** このマシンでは非対話 sudo が失敗する。`apt install` が必要になったら、実装を止めてユーザーに依頼する
- **`code` コマンドは PATH に無い。** VS Code は Flatpak 版（`com.visualstudio.code` 1.129）。
  拡張のデバッグ実行は VS Code の GUI から行う（F5 / Run Extension）。
  `flatpak run com.visualstudio.code` で CLI 起動は可能だが、Flatpak サンドボックス越しのパスに注意
- **`@vscode/test-electron` が動くかは M0 で必ず検証する。** 動かない場合は結合テストを諦め、
  ユニットテストに寄せる方針へ切り替えてよい（`docs/decisions.md` に記録すること）
- 一時ファイルは `/home/popos/scratch/` を使う。プロジェクト内に散らかさない
