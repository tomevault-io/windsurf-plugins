# LaLa — 個人用DAW

- アプリ名（表示名・成果物名）は **LaLa**。内部識別子（CMakeターゲット `daw`・bundle id `local.d0ne1s.daw`・`~/Music/daw/`・`~/Library/Logs/daw/`・配信repo `daw-releases`・Sparkle鍵アカウント `daw`）は旧名のまま（意図的。TCC・Sparkle・既存データの連続性のため変更しない）

## プロジェクト概要

### 目的
- Logic Proの機能過多による認知コストを削減するため、自分が本当に使う機能だけに絞った個人用DAWをJUCEでゼロから自作する
- 「全部入り」ではなく「引き算」が価値。機能追加の提案は常に「本当に自分が使うか」で判断する

### 非目的
- Apple純正音源（Logic付属音源）の代替は狙わない
- トラック数は〜50程度までを想定。数百トラック規模の運用は想定しない
- 商用配布・他人向けの汎用性は考えない

### サブ目的: 作りながら音楽の理解を深める

このアプリを作る過程で、音楽・音響・既存DAWの設計思想への理解を深めることもゴールに含む。そのための知識は専用ファイルに貯めず、**実装中の説明・提案・選択肢提示の書き方そのもの**で渡す。

**制作者の前提知識**（説明の粒度を決める基準）

- 制作歴3年。ただし「購入したビートの構成を切り直し、歌詞を書いてラップを録る」が主戦場。DAWのワークフロー用語（トラック・リージョン・構成・テイク・パンチイン・BPM・小節）は説明不要
- 作る曲のボリュームゾーンは**メロディアスな chill 系 hiphop で、トラップはたまに**（2026-08-06 /dig で確定）。機能・生成器の初期値やトレードオフの判断はこの前提に倒す
- EQ・コンプ・リバーブ・リミッターは**名前とレシピは知っているが原理を知らない**。「ボーカルにはハイパス」のような手順は知っていても、なぜそうするか・かけないとどうなるかが空欄になっている
- ゲインステージング・dBFS/ヘッドルーム・位相・サチュレーション・シンセの音作り・ドラムの音色選びはほぼ未知（ビートを買っていた＝この領域を外注できていた）
- ゼロからのビートメイクは1〜2曲のみ
- 統計・機械学習の用語は未知。AUC・p値・多重比較補正・相関係数は**都度、数値の読み方まで説明する**。数字を出したら「それが大きい/小さいとは何を意味するか」を1〜2文で添える

**説明・提案の作法**

- 機能の説明は、実装の話より先に「これは音楽的に何を解決する道具か」を1〜2文置く
- 「〜するといい」で終わらせず必ず因果で書く（レシピの丸暗記こそが脱したい状態）。ただし4文を超えたら削る
- 数値（`-0.3dBFS`・`20ms`・`Q=1.4` 等）を出したら、その値である理由を一言添える
- Logic / 一般的なDAWでの呼び名を併記する。LaLa独自語で完結させると外で得た知識と接続できなくなる
- 用語の注釈は初出時のみ。2回目以降は付けない
- 選択肢を出すときは、実装コストではなく**音楽的な結果**（聴こえ方・作業の速さ）でトレードオフを書き、「他のDAWはどちらを選んでいて、なぜか」を添える。「世の中のソフトが複雑な理由」を知る近道になる
- ビートメイク側（ドラム・シンセ・音色）の機能は経験が薄い前提で厚めに補う。逆に録音・構成側は本人の実地経験の方が確かなので、判断に迷ったら先に「Logicではどうしてた?」と聞く
- 深掘りは押し付けず「聞きたければ」のフックを1行置くに留める
- 歴史的経緯・逸話は幻覚しやすい領域。確度が低いときは断定せず、その旨を明示する
- **知識を理由に機能追加を勧めない**。知識の使い道は「意味が分かった上で捨てる」判断に倒れるのが健全（Logicとの差が「知らないから無い」から「知った上で無い」に変わる）

### 操作設計の方針
- キーボードショートカットは Logic Pro のデフォルトキーコマンドに合わせる（例: `r` = 録音、`m` = ミュート、`⌘←/→` = 横ズーム）。新しい操作を追加するときは、まずLogicの割り当てを確認してから決める
- ただし本人の好みが確定しているものはそちらを優先する（例: `,`/`.` = 1拍シーク・`Shift+,`/`.` = 1小節シーク。Logicの小節単位とは異なる）
- ビジュアル（音量バー・フェーダー・メーター等）もLogicのルックと読み方に準拠する。メーターは固定dBスケール（-60〜0dBFS・フェーダー位置と独立＝大きい信号はつまみを追い越す）、色は緑→黄→赤。常設のdB数値表示はミキサー/FXパネルのみに置き、常時見えるヘッダーには置かない（ドラッグ中ポップアップのみ）— Logicの配置と同じで、引き算の方針とも整合する
- undoの粒度は「ユーザーから見た1操作＝1件」で判定する。値を変える経路が複数あるなら（ドラッグ・ダブルクリック・数値クリック・ホイール等）**全経路で区切りを揃える**。1つ漏れると⌘Zの戻り先が変わり、「戻したはずが中間値」になる。経路を減らして揃えるのも有効な手段（使わない経路は無効化する）
- **仮配置・プレビュー系の機能は、キャンセルで巻き戻せない副作用を確定操作まで遅らせる**。SR確定・dirty化・ファイル書き出し・undo履歴への追加は「残す」の瞬間に一括で行い、プレビュー段階はメモリ内の変更（＋セッションbaselineで復元可能な値）だけに留める。プレビュー中に副作用を起こすと、キャンセル・失敗経路の数だけ復元処理が必要になり漏れが生まれる（ループ採用のSR確定で実際に3回レビュー指摘を受けた）

### ショートカットキーの追加ルール
- 定義は `Source/ui/Shortcuts.h` のテーブルが単一の真実の源。追加時は必ずここに1行足し（ID・カテゴリ・説明・表示用keyLabel・判定matcher）、`MainComponent::keyPressed` では `Shortcuts::matches()` で判定する（KeyPress直書き禁止）
- ボタンのツールチップ・右クリックメニューのショートカット表記は `Shortcuts::tooltipText()` / `Shortcuts::keyText()` から生成する（表記文字列の手書き禁止）
- ⌘?一覧（`ShortcutListOverlay`）はテーブル走査で自動生成されるため、追加時の個別対応は不要

## 現在地とゴール

**Tier 1（マルチトラック録音）と Tier 2（MIDI打ち込み・ミキサー・FX）は実装済み**。現在の主戦場はリファレンス駆動ビートメイク（[reference-beat.md](docs/design/reference-beat.md) のフェーズ進行）。機能の詳細仕様は `docs/plans/` の各planが真実の源。

実装済みの大枠（「無いと思って再実装」を防ぐための一覧。個別仕様はplanを見る）:

- **オーディオ**: マルチトラック録音（カウントイン・メトロノーム）・リージョン操作（分割・移動・フェード・ゲイン・ミュート・リピート/ループ・移調/タイムストレッチ〔非破壊・v20〕）・トラック並べ替え・サイクル再生・セクションマーカー・バウンス/リージョン書き出し・曲末フェード。**端ドラッグリサイズ（トリム）はMIDIリージョンのみ**（オーディオは意図して未実装）
- **取り込み**: オーディオファイルD&D（wav/aiff/flac/mp3/m4a→24bit WAVクリップ変換）・URL取り込み（yt-dlp）・右パネルのファイルブラウザ（`~/Downloads`起点・プレビュー再生付き）・MIDIファイル取り込み
- **MIDI**: MIDIトラック・ピアノロール・内蔵GM音源（DLSMusicDevice・厳選8音色＋ドラム）・サンプラー音源（サンプル割当）
- **ミキサー・FX**: 音量・パン・ミュート/ソロ・センドバス（Reverb A/B・Delay）・トラックEQ/Comp・バス/MasterのFX（常在・バイパスなし）
- **ボーカルのピッチ補正**（クリップ単位・非破壊・独立ウィンドウ。YIN 検出＋WORLD 再合成・自動スナップ＋ノート手直し・横移動は隣接吸収・解析はサイドカー世代保存）
- **リファレンスビート**: 参照曲の分析（Python外部パイプライン・並列実行）・アプリ内レポート・ドラム/ベースガチャ・ループトラック・制約カード・アンカーカード
- **配布**: Release版のSparkle自動アップデート（`daw-releases`）

まだ作らないもの:

- 汎用AU/VSTプラグインホスティング（Ext 枠は 2026-08-22 に廃止。理由は fx-roadmap.md「削った候補」。内蔵GM音源の固定ホストとは別物）
- UI面の意図的な見送りは [ui-principles.md](docs/design/ui-principles.md) の見送りリスト、機能の要否判断は [feature-scope.md](docs/design/feature-scope.md) を参照
- 現在のフェーズのスコープ外の実装を先回りして入れない（抽象化のしすぎに注意）

## 設計判断の参照先

複数の実装にまたがる方針は `docs/design/` にある。着手前に関係するものを読む。

- [feature-scope.md](docs/design/feature-scope.md) — 制作スコープの3層と機能の要否判断（使用頻度×複雑さの恒常的なコスト）。**機能追加を検討・提案する前に必ず読む**
- [ui-principles.md](docs/design/ui-principles.md) — 情報の強弱・画面の性格別の方針・日英混在のフォントサイズ・**意図的な見送りリスト**。UI追加時とUIレビュー対応時に読む
- [grid-resolution.md](docs/design/grid-resolution.md) — グリッド解像度の上限（タイムライン1/16・マーカーは拍・将来のピアノロールの要件）
- [transport-playhead.md](docs/design/transport-playhead.md) — 再生ヘッド（今いる場所＝編集の基準）と再生開始位置（次に鳴る場所）の分離。停止・録音・シークで両者がどう動くか。**トランスポートや「止めた場所」に関わる機能を触る前に読む**
- [mixer-fx.md](docs/design/mixer-fx.md) — Tier 2 ミキサー・FXの確定設計（画面構成・チャンネル構成・6スライス）
- [fx-roadmap.md](docs/design/fx-roadmap.md) — EQ・Comp後の残りFX・メーター群の実装順（5バッチ格子・耳セッションの方針・削った候補）。**新しいFX/メーターに着手する前に読む**
- [region-settings.md](docs/design/region-settings.md) — リージョン設定UIの割り当て方針
- [arrangement.md](docs/design/arrangement.md) — 少ない要素で作る方針と曲の尺・構成（90〜180秒・ボリュームゾーン120秒／verse-hook系の3構成／hookを先に作りverseは抜きで作る／常時鳴るのは5枠・足すならhookだけに1枠）。**ビートの編成や曲の構成を組む前に読む**
