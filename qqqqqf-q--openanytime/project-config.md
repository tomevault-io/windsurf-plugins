# OpenAnytime Agent Working Agreement

本文件适用于仓库根目录及其所有子目录。任何人或自动化 Agent 在读取、修改、运行、部署或排障本项目之前，都必须先阅读并遵守本文件。

## 1. 项目性质与风险等级

OpenAnytime 是鱼跃 5 HSE（安耐糖 / Anytime CGM）的逆向研究与本地数据采集项目。产品实物型号由用户确认为 5 HSE；现有逆向记录中抄录的 `CT5` 只是尚未用原始日志和反编译产物复核的内部字符串，不得据此改写产品型号或宣称官方协议名称。仓库中的代码会处理：

- 连续血糖与温度等健康数据；
- 传感器序列号、BLE 地址和广播原始数据；
- 设备专属参数，例如 `sureClose`；
- 本地 SQLite 数据库、JSONL 原始采集记录和运行日志。

这些数据不是普通缓存。即使某些读数理论上可以从广播或 JSONL 重新解析，也不能假设历史数据完整、仍可重新获取或能够无损重建。

当前项目仍是逆向原型，不具备成熟生产系统应有的全部保护。缺少保护不是降低操作标准的理由；相反，在相关保护完成前，必须采用更保守的工作方式。

## 2. 最高优先级原则

以下规则不可被“方便调试”“重新生成更快”“数据库很小”或“只是本地项目”等理由覆盖：

1. **数据库和原始采集数据属于受保护的用户数据，不属于可随时删除的构建产物。**
2. **默认只读。** 未得到用户对具体写操作的明确授权，不得修改生产数据。
3. **不得静默重建。** 预期数据库缺失、为空、损坏或 schema 不匹配时必须停止并报告，不得自动创建一个空数据库掩盖问题。
4. **不得把“应用能启动”作为“数据安全”的替代标准。** 空库启动成功属于数据事故，不属于恢复成功。
5. **任何可能破坏、覆盖或迁移数据的操作都必须先备份、再验证、后执行。**
6. **恢复必须写入新文件。** 在恢复结果通过验证且用户明确同意替换前，不得覆盖原数据库。
7. **不确定时停止写入。** 无法确认数据库路径、进程所有权、schema 或备份状态时，只能继续只读调查。

## 3. 受保护的数据和路径

至少把以下内容视为受保护数据：

- `cgm.db`；
- `cgm.db-wal`、`cgm.db-shm`、`cgm.db-journal`；
- 任何 `*.db`、`*.sqlite`、`*.sqlite3` 及其 WAL、SHM、journal 文件；
- `cgm_*.jsonl`；
- `raw_samples.txt` 和其他原始广播捕获；
- `latest.txt`，虽然它不是完整历史，但仍包含健康数据；
- `*.log`、`*.err`，发生故障时它们可能是恢复和审计证据；
- 包含设备名、序列号、BLE 地址、传感器码、密钥或个人健康读数的导出文件。

已知运行目录可能包括：

- 当前 Git checkout；
- `~/Library/Application Support/cgm-data/`；
- launchd 配置或其他启动脚本指定的目录。

不得仅根据当前工作目录猜测哪一份是生产数据。修改前必须检查实际运行进程、launchd 配置、脚本路径、数据库文件元数据和打开文件，确认真正的数据源。

`.gitignore` 只负责避免隐私数据进入 Git，不是备份策略。尤其禁止使用可能删除 ignored 文件的命令，因为 `cgm.db` 正是 ignored 文件。

## 4. 明确禁止的操作

除非用户在了解准确路径、影响、备份和回滚方案后明确授权，否则禁止：

- 删除、清空、截断、覆盖、替换、移动或重新命名生产数据库；
- 删除数据库的 WAL、SHM 或 journal 文件；
- 执行 `DROP TABLE`、`DROP INDEX`、无约束 `DELETE` 或其他破坏性 SQL；
- 为“修复 schema”而删除数据库并重新执行 `CREATE TABLE`；
- 把空数据库、测试数据库或仓库副本覆盖到运行目录；
- 对运行目录执行带删除语义的同步或部署；
- 修改数据库及其父目录的所有者、权限或 ACL 来绕过错误；
- 在生产数据库上直接试验迁移、手工 SQL 或未验证脚本；
- 为了验证功能而启动会写生产数据库的采集器；
- 用浏览器、API 测试或测试套件写入真实健康数据；
- 在 Issue、PR、提交信息、终端摘要或面向用户的输出中泄露实际健康读数和设备身份信息。

特别禁止在可能包含受保护数据的目录运行：

```text
rm cgm.db*
rm -rf <runtime-directory>
find <runtime-directory> -delete
git clean -fd
git clean -fdx
git clean -X
rsync --delete ... <runtime-directory>
sqlite3 cgm.db 'DROP ...'
sqlite3 cgm.db 'DELETE FROM ...'
cp /dev/null cgm.db
```

以上只是示例，不是完整黑名单。任何具有等价效果的命令、脚本或库调用同样禁止。

## 5. 用户授权要求

读取、修改代码不等于获得修改数据的授权。用户要求“修数据库”“重置”“重新初始化”“清理环境”时，如果操作含义可能涉及数据丢失，必须先说明并等待明确确认。

请求授权时必须给出：

1. 将操作的绝对路径；
2. 当前数据库大小、修改时间和基本状态；
3. 准备执行的具体写操作；
4. 哪些数据可能改变或丢失；
5. 备份文件的绝对路径和创建方式；
6. 回滚方式；
7. 操作后的验证标准。

“我会处理数据库，可以吗”不构成有效说明。用户只批准某一步时，不得把授权扩展到替换数据库、重启服务、删除旧文件或修改 launchd 配置。

## 6. 只读调查协议

排障的第一阶段必须只读。建议按以下顺序调查：

1. 确认 `pwd`、Git 分支和 `git status`；
2. 找出可能的数据库文件，但不要打开为可写模式；
3. 检查 launchd、运行进程、命令行参数和源代码路径；
4. 记录数据库绝对路径、inode、大小、创建时间和修改时间；
5. 检查同目录的 WAL、SHM、journal、JSONL、日志和备份；
6. 以只读方式查看 schema、`PRAGMA user_version`、表名和索引；
7. 运行只读的 `PRAGMA query_only=ON` 与 `PRAGMA integrity_check` 或 `quick_check`；
8. 只统计行数、最早时间、最晚时间和关键唯一性，不先输出具体健康数据；
9. 对比代码期望 schema 与实际 schema；
10. 报告事实、未知项和下一步，不在调查过程中顺手修复。

使用 SQLite CLI 时优先使用 `sqlite3 -readonly`。Python 调查代码必须使用 SQLite URI 的只读模式，并立即设置查询保护：

```python
sqlite3.connect(f"file:{db_path}?mode=ro", uri=True)
connection.execute("PRAGMA query_only = ON")
```

不得用普通的 `sqlite3.connect(path)` 判断数据库是否存在，因为文件不存在时它会创建空数据库。必须先用文件系统检查确认目标存在，再以只读模式打开。

## 7. 数据库缺失、空库或异常时的行为

如果预期数据库不存在：

- 立即停止会写数据的服务或启动尝试，但不要删除任何文件；
- 不得创建同名空数据库；
- 检查实际服务路径、配置、旧目录、备份、JSONL、WAL、SHM 和日志；
- 报告“数据库缺失”，不要把它描述为“首次启动”；
- 只有显式的全新安装流程才能创建新库。

如果数据库存在但预期表不存在或行数异常为零：

- 视为潜在数据事故；
- 不得运行 `CREATE TABLE IF NOT EXISTS` 来掩盖异常；
- 保留文件元数据和日志；
- 不得继续采集并向异常数据库写入新数据，以免覆盖恢复线索或混合时间线；
- 在新路径中进行恢复和验证。

如果数据库损坏：

- 不在原文件上运行修复；
- 先冻结写入并制作一致性快照；
- 在副本上尝试 `.recover`、备份恢复或数据导出；
- 保存恢复日志和失败证据；
- 对恢复结果进行 schema、完整性、计数和时间范围验证；
- 只有用户确认后才切换生产路径。

## 8. 备份规则

任何获准的 schema 或数据写操作前都必须创建备份。备份要求：

- 路径不能与原数据库相同；
- 文件名包含 UTC 时间戳和操作说明；
- 优先使用 SQLite Backup API、`.backup` 或经过验证的一致性快照方式；
- 数据库正在 WAL 模式运行时，不得只复制主 `.db` 文件并假设它完整；
- 如果选择停服务后复制，必须确认写进程已完全退出；
- 备份后以只读方式运行完整性检查；
- 记录表行数、最早/最晚时间、schema 版本和文件哈希；
- 不得在验证完成前执行原计划写操作；
- 不得因为操作成功而自动删除备份。

备份文件同样包含敏感健康数据，必须保持本地、限制权限，不得提交 Git 或上传到未获授权的位置。

## 9. Schema 与迁移规则

数据库 schema 必须只有一个权威定义。Web 服务、采集器和工具不得各自复制一份 `CREATE TABLE`。

成熟实现必须满足：

- 使用 `PRAGMA user_version` 或专门的 migration 表记录版本；
- 每个版本变化都有独立、可审查、可测试的前向迁移；
- 启动时检测 schema，不由读取服务创建或修改 schema；
- schema 不符合预期时 fail closed，输出可操作错误；
- migration 在事务中执行，失败时完整回滚；
- migration 执行前自动创建并验证备份；
- migration 对每个受支持旧版本都有升级测试；
- 需要丢列、重建表或重写大量数据的迁移必须单独获得用户授权；
- 不得用删除数据库代替 migration；
- 不得依赖服务启动顺序获得正确约束或索引。

`CREATE TABLE IF NOT EXISTS` 只能用于明确的首次初始化命令，不能作为生产启动时的隐式迁移机制，因为它不会验证已有表的列、约束和索引是否正确。

首次初始化必须是显式操作，例如未来的 `openanytime init-db --path ...`，并满足：

- 目标文件已存在时拒绝执行；
- 父目录不符合预期时拒绝执行；
- 清楚显示将创建的绝对路径；
- 创建后写入 schema 版本并进行完整性检查；
- 不与服务普通启动混在一起。

## 10. 数据写入规则

采集数据应采用追加和幂等语义：

- 明确定义广播 counter 回绕、重复包、乱序包和设备更换时的身份规则；
- 使用可解释的唯一键和显式 upsert；
- 不使用宽泛的 `INSERT OR IGNORE` 静默吞掉未知完整性错误；
- 重复数据不能导致采集器崩溃，也不能生成重复读数；
- 一个广播包及其 readings 必须在同一事务中提交；
- 任何异常都必须回滚整个事务；
- 错误日志不得包含不必要的完整健康数据或设备密钥；
- 连接必须可靠关闭，并设置合理的 `busy_timeout`；
- WAL、同步级别和 checkpoint 策略必须明确记录并经过故障测试。

不得通过修改文件权限来解决写入失败。`readonly database` 首先表示路径、所有者、运行用户或部署方式存在问题，必须先查清原因。

## 11. 运行时边界

长期运行的采集器应是数据库的唯一写入者。Web/API 服务原则上只读：

- 读取服务使用只读 SQLite 连接；
- Web 服务不得创建数据库或 schema；
- 默认只监听 loopback；
- 暴露到局域网或公网必须有用户明确授权、访问控制和威胁评估；
- API 参数必须验证并限制范围；
- 不允许客户端执行任意 SQL；
- 运行目录与源码 checkout 分离；
- 数据路径通过明确配置提供，不依赖脚本所在目录；
