# AGENTS.md

Zcv 是一个以本地编辑体验为核心的代码编辑器项目。

修改代码前，应先理解相关架构和已有实现。Zed 是 Zcv 的主要参考实现；当修改涉及 Zed 已经解决的编辑器能力时，优先研究其实现和设计，再决定如何在 Zcv 中实现。

## 开发阶段原则

Zcv 当前处于快速演进阶段。

**架构正确性优先于向后兼容。**

在没有明确兼容要求时：

- 可以删除、重命名或重新组织已有实现。
- 不维护新旧两套逻辑。
- 不为了兼容错误的历史设计增加适配层。
- 相关调用方、测试和文档应在同一次修改中一起更新。
- 优先建立正确的长期架构，而不是通过局部补丁维持当前实现。

如果一个需求暴露出底层抽象错误，应优先修正抽象，而不是继续在错误抽象上增加条件分支。

## 项目范围

以下是当前阶段明确的项目范围。

### Zed

Zed 是 Zcv 编辑器架构和功能实现的重要参考。

当修改涉及编辑器已有成熟实现时，可以查阅本机：

```text
macOS：/Users/liuyuan/project/zed
Windows：D:\project\zed
```

重点理解：

- 模块职责如何划分；
- 状态由谁拥有；
- 数据如何流动；
- 生命周期如何管理；
- 编辑器核心抽象如何组合；
- 边界条件如何处理。

不要为了形式一致而机械复制 Zed。

Zcv 与 Zed 的项目范围、已有抽象或依赖不同的地方，应按照 Zcv 自身架构进行调整。只有在设计目标和上下文一致时，才直接采用对应实现。

### 远程与协作

当前不为 Zcv 引入：

- 实时协作；
- 远程开发；
- 与上述能力直接相关的基础设施。

不要为了潜在的未来需求提前设计这些能力。

### 语言智能

当前阶段暂不引入 LSP。

语法层面的能力，包括但不限于：

- 语法高亮；
- 语法节点识别；
- 基础语法感知；
- 基于语法树的编辑能力；

统一优先依赖 Tree-sitter 以及对应的 `.scm` 查询文件。

不要为了实现当前需求提前建立 LSP 抽象或兼容层。

未来正式引入 LSP 时，再重新设计相关能力抽象。

## 修改代码前

修改代码前，根据修改范围读取相关文档和实现。

至少确认：

1. 当前模块的职责。
2. 调用方和消费方。
3. 数据和状态的所有者。
4. 是否已有相同或相近能力。
5. 是否存在相关文档或项目约定。
6. Zed 是否存在值得参考的对应实现。

不要无条件读取整个 `docs/` 目录。

优先阅读：

```text
AGENTS.md
相关目录中的 AGENTS.md
相关架构文档
相关模块 README
修改代码直接引用的设计文档
```

如果文档继续引用其他规范，再沿引用关系读取。

## 修改权限

读取代码、搜索仓库、阅读文档、查看 Zed 源码以及进行其他只读分析不需要额外授权。

修改仓库文件必须来自开发者明确提出的修改任务。

一次明确的代码修改请求，视为对该任务合理范围内文件修改的授权，不需要为每一个文件重复请求许可。

出现以下情况时，应重新确认：

- 修改范围明显超出原始任务；
- 需要删除大量代码或文件；
- 涉及不可逆的数据操作；
- 存在多个会显著影响架构方向的方案，且无法根据现有设计判断；
- 需要修改任务明确排除的模块。

## 架构规范

### 单一编辑器承载所有文档形态

Zcv 从始至终只有一个 `Editor`。普通文档、组合文档以及差异、搜索等文档形态，都是编辑器展示内容的差异，不是不同的编辑器，也不是不同的编辑逻辑。所有文档都应共享同一套选择、滚动、输入、编辑、折叠、命中测试和渲染管线。

修改编辑器或文档展示能力时，AI 必须把这条规则作为架构约束，不得按文档形态复制 `Editor`、建立普通文档与组合文档两套编辑流程，或分别维护平行的交互状态。文档内容组织、源坐标映射、可编辑性和显示投影的差异，应收敛在对应的文档模型与显示层；新增行为应优先扩展唯一的 `Editor` 管线。不同构造入口只表达输入场景或内容来源，不代表不同编辑器实现。

### 架构优先于补丁

实施任何非机械修改时，首先判断问题属于：

```text
局部实现错误
还是
底层抽象错误
```

如果是底层抽象错误，应修正抽象。

禁止通过不断增加以下机制来掩盖架构问题：

- 特殊分支；
- 回退逻辑（fallback）；
- 兼容路径；
- 隐式默认行为；
- 一次性状态；
- 绕过正常生命周期的调用。

如果局部修复必须依赖越来越多特殊条件，应重新检查当前抽象是否正确。

### 跨平台架构

跨平台支持必须围绕语义能力建立统一入口，而不是让调用方分别拼接各平台流程。

- 业务层只依赖平台无关的能力接口或门面；平台差异由对应能力域的私有后端、适配模块或平台实现承载。
- 统一入口表达稳定语义，例如“终止当前进程树”“准备应用更新”“原子替换安装目录”，不暴露 `cfg`、平台路径、系统命令或平台资源布局。
- 同一能力的跨平台流程应共享状态机、错误处理和生命周期；只有系统调用、路径布局、权限、进程模型等真实差异留在平台边界内。
- 不建立包罗万象的全局 `Platform` 或万能平台 crate。只有两个或更多能力域拥有相同且稳定的语义、生命周期和错误契约时，才提取共享平台原语；否则将后端放在实际消费方附近。
- 平台后端必须明确创建者、所有者、调用者和销毁时机；不得通过业务层散落的条件编译、隐式回退或双轨流程维持平台一致性。
- 新增平台时，应优先新增或替换后端实现，不复制一套业务流程；平台无关测试覆盖共同语义，平台测试只覆盖后端契约和系统边界。

跨平台重构应先绘制“能力域 → 统一入口 → 平台后端”的依赖图，再按真实消费方决定模块归属。
更新、终端进程、Git 进程树、文件监视、路径和设置等能力可以各自拥有边界；“统一入口”不等于把所有平台行为集中到一个全局抽象中。

### 高内聚

代码应放在真正拥有其语义、状态和生命周期的模块中。

只服务单一消费方、且不形成独立语义边界的局部实现，通常可以与消费方放在一起。单一消费方本身不能决定代码归属；即使只有一个直接调用方，只要代码具有独立的领域职责、状态、生命周期或测试边界，也应放在对应的领域模块中。

例如：

```text
window_controls 只由 top_bar 使用

→ shell/components/top_bar/window_controls.rs

而不是：

→ shell/components/window_controls.rs
```

不要仅因为代码“可能以后复用”就提前提升到公共层。

### 低耦合

存在两个或更多真实消费方时，可以考虑提取共享原语；但共享方数量不是提取模块的必要条件。应先确认代码是否已经形成稳定、内聚的能力边界，再决定是否独立成模块。

例如：

```text
bar_frame / glyph / bar_region
同时被 top_bar 和 bottom_bar 使用

→ shell/components/primitives/
```

消费方应共同依赖共享原语，而不是彼此依赖。

判断顺序：

1. 确定代码表达的语义和领域职责。
2. 确定状态所有权、生命周期和主要维护者。
3. 确定它是否形成独立且可测试的能力边界。
4. 根据依赖方向决定模块归属，避免让领域模块反向依赖具体消费方。
5. 将真实消费方数量作为辅助信号，而不是模块归属的决定条件。
6. 没有稳定边界和真实需求时，不要提前抽象公共模块。

### 所有权必须明确

新增状态或能力时，应明确：

- 谁创建它；
- 谁拥有它；
- 谁可以修改它；
- 谁消费它；
- 生命周期何时开始；
- 生命周期何时结束。

避免通过全局状态、隐式注册、跨模块访问或临时桥接模糊所有权。

如果无法明确说明某个状态由谁负责维护，通常说明当前模块划分仍然存在问题。

### 单一数据源

同一项事实必须只有一个权威数据源。

任何状态、配置或业务事实，都应明确由一个位置负责存储和维护。其他模块如果需要相同信息，应读取、引用或从权威数据源派生，而不是维护另一份需要同步的副本。

禁止为同一项事实建立多个可以独立修改的数据源。

尤其避免：

- 在多个模块中分别保存同一状态；
- 为方便读取而复制一份长期存在的影子状态；
- 同一配置同时存在多个独立来源；
- 同一业务事实既保存在模型中，又在 UI 或其他模块中维护另一份可写副本；
- 修改一项状态时需要手动同步多个位置；
- 通过双写、双向同步或补偿逻辑维持多个副本的一致性；
- 在派生数据失效后尝试反向修复权威数据。

派生数据不属于新的权威数据源。

如果某项数据能够从权威数据源确定性地计算得到，应优先在需要时计算，或者作为可丢弃、可重建的缓存保存。

例如：

```text
文档内容
→ 文档模型是权威数据源

UI 中显示的文本、行号、选择状态投影
→ 从文档模型或对应状态派生
→ 不维护另一份独立可写的文档内容
```

### 显式优于隐式

模块之间的行为应显式表达。

不要把重要业务行为隐藏在：

- 隐式回退；
- 隐式默认值；
- 副作用初始化；
- 不透明的自动注册；
- 调用方无法看到的状态修复。

如果存在默认值或策略选择，应由负责该决策的模块显式完成。

跨模块调用时，应让调用方能够从接口本身理解主要行为，而不是依赖隐藏的全局规则。

## 实现原则

### 编码前思考

不要根据名称或局部代码猜测行为。

实施前明确：

- 需求是什么；
- 当前实现为什么不能满足需求；
- 哪些模块真正需要改变；
- 修改后的成功条件是什么。

存在多个合理方案时，应比较它们的架构影响，而不是默默选择其中一种。

对于可逆、局部且低风险的歧义，可以采用最符合现有代码和项目原则的方案，并在回复中说明假设。

只有当歧义会显著改变架构、数据或修改范围时，才需要停止并询问开发者。

### 最小必要实现

只实现当前需求需要的能力。

不要：

- 添加未经请求的功能；
- 为假设中的未来需求增加配置；
- 为单一调用方创建抽象层；
- 为静态类型已经保证的不可能情况增加防御逻辑；
- 建立当前没有真实消费者的接口；
- 为“以后可能会用”提前设计扩展点。

如果实现明显比问题本身复杂，应重新检查抽象是否正确。

能通过删除错误抽象解决的问题，不要通过增加更多抽象解决。

### 精准修改

只修改解决当前问题需要的代码。

不要顺手：

- 重构无关模块；
- 调整无关格式；
- 重命名无关符号；
- 修改无关注释；
- 清理历史遗留代码。

如果本次修改使已有代码变成无用代码，应一起删除由本次修改直接产生的：

- 未使用的导入；
- 未使用的变量；
- 未使用的函数；
- 已失效的分支。

发现与当前任务无关的问题时，可以在回复中指出，但不要顺手修改。

每个修改片段都应能解释为：

```text
需求本身
必要的配套修改
或
本次修改直接产生的清理
```

不要借当前任务扩大修改范围。

### 不做推测性实现

不要因为某种场景“以后可能出现”就提前增加：

- 配置项；
- 抽象接口；
- 兼容逻辑；
- 回退逻辑；
- 状态字段；
- 扩展点；
- 错误恢复机制。

只有存在当前真实需求或明确消费方时，才引入对应能力。

### 信任类型系统

对于 Rust 类型系统已经在同一进程的受控代码中保证的条件，不要重复增加运行时校验。

运行时校验应集中在真正存在不可信输入的位置，例如：

- 用户输入；
- 文件输入；
- 配置文件；
- IPC；
- 网络协议；
- 外部进程输出；
- 持久化数据；
- FFI；
- 第三方库返回的不受控数据。

不要通过大量“不可能发生”的错误处理掩盖类型设计问题。

## 验证

修改必须有明确的成功条件。

例如：

```text
修复错误
→ 能稳定复现原问题
→ 修改后复现用例通过

新增行为
→ 为目标行为添加测试
→ 测试能够证明该行为存在

重构
→ 原有行为测试保持通过
→ 新结构满足新的架构要求
```

多步骤修改开始前，可以简要列出：

```text
1. 修改内容 → 验证方式
2. 修改内容 → 验证方式
3. 修改内容 → 验证方式
```

验证应与修改范围匹配。

优先运行最小、最相关的验证，不要默认运行与修改无关的整个测试集合。

不要运行全量测试。全量测试由开发者人工执行；只有开发者明确要求时，才可以运行全量测试。
