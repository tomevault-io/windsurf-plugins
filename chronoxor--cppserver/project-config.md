# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository purpose

CppServer is a cross-platform C++ library (`namespace CppServer`) providing asynchronous TCP/SSL/UDP/HTTP/HTTPS/WebSocket(S) server and client primitives built on top of standalone Asio + OpenSSL, plus an optional message-protocol layer generated from Fast Binary Encoding (FBE). It ships as a static library (`cppserver`) consumed via headers under `include/server/...`, plus an optional `proto` library, examples, performance benchmarks, and Catch2-based tests.

## Dependency model: `gil` + `modules/`

External dependencies are not vendored as git submodules. Instead they are pulled in by the [`gil`](https://github.com/chronoxor/gil) tool from `.gitlinks`, which clones each into `modules/` and also fetches the `build/` (CppBuildScripts) and `cmake/` (CppCMakeScripts) helper repos as siblings. **After any fresh clone, `gil update` must be run before `cmake` — without it `modules/asio`, `modules/CppCommon`, `modules/Catch2`, `modules/cpp-optparse`, `modules/CppBenchmark`, `modules/OpenSSL`, and `www/api/swagger` are empty and the build fails immediately.** `gil` itself is installed via `pip3 install gil`.

`modules/CMakeLists.txt` simply `include()`s per-dependency `.cmake` files in the same directory — that is where each third-party target is defined.

## Build & test

The repo uses the vendored `build/` scripts (see `build/CLAUDE.md` for their internal contract). Standard flow, from the repo root:

```sh
cd build && ./unix.sh          # Linux/macOS: generate → build → test → install into bin/
cd build && ./mingw.bat        # Windows MinGW
cd build && ./vs.bat           # Windows Visual Studio (RelWithDebInfo, x64)
```

The wrappers `cd ../..` internally and configure into `temp/` with install prefix `temp/install`. Final artifacts land in `bin/` at the repo root. `./build/Unix/07-coverage.sh` reconfigures with `-DCODE_COVERAGE=ON` and produces `temp/coverage/coverage.html`.

Run individual numbered steps from inside the toolchain dir (e.g. `cd build/Unix && ./02-build.sh`) — they assume that working directory.

### Tests

`cppserver-tests` is a single Catch2 v3 binary built from every `tests/*.cpp` and linked against the `Catch2` target from `modules/`. Tests run via `ctest` (see `add_test(... --durations yes --order lex)` in the top-level `CMakeLists.txt`). To run a single Catch2 test case directly, invoke the built binary:

```sh
./bin/cppserver-tests "<test-case-name-or-tag>"   # e.g. "[TCP]" or "TCP server"
./bin/cppserver-tests --list-tests
```

On Unix, `build/Unix/03-tests.sh` deliberately swallows test failures with `|| true`; the MinGW and VS variants do not. Don't "fix" the Unix variant to be strict without checking why it was permissive.

## Code layout

- `include/server/` — public headers, grouped by transport:
  - `asio/` — `Service` (the IO host), TCP/UDP/SSL clients, servers, sessions, resolvers, `Timer`, `SSLContext`, plus a custom Asio allocator (`memory.h`).
  - `http/` — HTTP/HTTPS clients, servers, sessions, `HTTPRequest`/`HTTPResponse`. Built on top of `asio/tcp_*` and `asio/ssl_*`.
  - `ws/` — WebSocket(S) clients, servers, sessions. WS builds on HTTP for the handshake, WSS on HTTPS.
- `source/server/` — `.cpp` implementations mirroring the header tree exactly. New transport code must add files in both trees (the top-level CMake glob picks them up automatically — no list to edit).
- `proto/` — the optional protocol library:
  - `simple.fbe` is the **only** hand-written file. Everything else (`fbe.{h,cpp}`, `fbe_models.*`, `fbe_protocol.*`, `simple.{h,cpp}`, `simple_models.*`, `simple_protocol.*`) is generated by `fbec` (the FBE compiler). Regenerate with `fbec --cpp --proto --input=simple.fbe --output=.` from `proto/`; do not hand-edit the generated files.
- `examples/` — one executable per `*.cpp` (target name `cppserver-example-<basename>`). Used as documentation in the README.
- `performance/` — one executable per `*.cpp` (target name `cppserver-performance-<basename>`), linked against `cppbenchmark`. These are the benchmarks reported in the README.
- `tests/` — Catch2 v3 test sources; all `.cpp` are compiled into the single `cppserver-tests` binary.
- `tools/certificates/` — pre-generated dev CA, server, client certs and Diffie-Hellman params used by the SSL/HTTPS/WSS examples and tests. Regenerate via `generate.sh` / `generate.bat`. **Passphrase is hard-coded as `qwerty` — these are development-only and must never be reused in production.**
- `www/` — static assets served by HTTP examples; `www/api/swagger/` is populated by `gil` from `modules/swagger-ui`.

## Architectural conventions

- **One `Asio::Service` hosts many clients/servers.** A `Service` owns either one IO thread (default) or a thread pool. Two construction modes matter when reading code:
  - `Service(threads, false)` → io-service-per-thread, no strands required.
  - `Service(threads, true)` → single io_service over a thread pool, strands required to serialize per-session handlers.
