# View / API 설계 방침
## 목표
* View는 HTTP 입력, 화면 조립, 리다이렉트만 담당한다.
* API는 데이터 조회·수정, 권한 검사, 입력 검증, 트랜잭션 경계를 담당한다.
* API는 View 없이 단독으로 호출해도 정상 동작해야 하며, 호출자가 처리를 끝낼 수 있는 데이터 또는 명확한 오류를 반환한다.
* 새 라우트는 쿼리 파라미터 대신 경로 파라미터를 사용한다. 기존 URL 호환성은 라우트 변경이 명시된 경우가 아니면 유지한다.
* 기존 동작을 유지할 수 있는 가장 작은 구현을 우선한다. 실제 중복 제거 또는 View/API 책임 분리에 필요하지 않다면 추상화를 추가하지 않는다.
* 작업 목적과 직접 관련 없는 파일 정리, 이름 변경, 스타일 통일, 추상화 변경, 대규모 리팩터링은 하지 않는다.
* 기능을 추가하기 위해 시스템 전체를 복잡하게 만들지 않는다. 기존 구조와 호환성을 최대한 유지하면서 필요한 기능을 가장 작은 코드와 가장 적은 의존성으로 구현한다.
## 코드 스타일 원칙
* 변수명과 함수명에는 `snake_case`를 사용한다.
* 함수명은 반드시 첫 글자를 대문자로 시작한다.
* API 함수명은 반드시 `Api_`로 시작한다. 예: `Api_document_get`, `Api_user_permission_check`.
* View 함수명은 반드시 `View_`로 시작한다. 예: `View_document`, `View_history`.
* API 파일명은 반드시 `api_`로 시작한다. 예: `api_document.go`, `api_user.go`.
* View 파일명은 반드시 `view_`로 시작한다. 예: `view_document.go`, `view_history.go`.
* API 기능을 `view_*.go` 파일에 구현하거나 View 기능을 `api_*.go` 파일에 구현하지 않는다.
* API 또는 View 역할을 하는 새 함수와 파일에 다른 접두사를 임의로 사용하지 않는다.
* 일반 내부 헬퍼처럼 API 또는 View에 해당하지 않는 함수는 해당 역할의 접두사를 강제로 붙이지 않되, 함수명의 첫 글자는 대문자로 시작하고 `snake_case`를 사용한다.
* 새 함수에 `camelCase` 또는 `PascalCase` 형태의 이름을 사용하지 않는다.
* 변수명은 소문자 `snake_case`를 기본으로 한다. 예: `document_name`, `user_id`, `is_admin`.
* 상수와 기존 공개 인터페이스는 기존 코드와의 호환성을 우선하며, 스타일 통일만을 목적으로 이름을 변경하지 않는다.
* 기존 함수나 변수의 이름은 현재 작업에서 변경할 필요가 없다면 스타일 통일만을 위해 일괄 변경하지 않는다.
* 새 코드에서는 주변 코드가 다른 스타일을 사용하더라도 본 규칙을 우선한다.
* 이름은 가능한 한 역할을 직접 드러내도록 작성하며, 의미를 알기 어려운 지나치게 짧은 이름은 반복문 인덱스 등 명확한 경우를 제외하고 사용하지 않는다.
## View 및 UX/UI 원칙
* `view_*.go` 파일에서 SQL을 직접 작성하지 않는다.
* View 라우트와 View의 주요 처리 함수는 `View_*` 함수에 구현한다.
* View에 필요한 도메인 데이터는 기존 `Api_*` 함수로 먼저 가져온다.
* View는 언어, 템플릿, URL, HTML escape, UI 같은 표시용 헬퍼를 사용할 수 있다.
* 아직 API·도메인 함수로 옮기지 않은 기존 표시용 헬퍼가 필요한 경우에만 View에서 DB 연결을 유지한다.
* View가 DB 연결을 가지고 있는 것 자체는 기존 코드 호환을 위해 허용할 수 있지만, 새 직접 SQL을 추가하는 근거가 되지는 않는다.
* 권한 검사와 쓰기 입력 검증을 View에만 두지 않는다. View 검사는 UI 편의를 위한 보조일 수 있지만, API가 같은 규칙을 반드시 강제해야 한다.
* View는 API가 반환한 상태에 따라 화면 출력, 오류 표시, 인증 유도, 리다이렉트 등 HTTP 및 UI 처리를 수행한다.
* 사용자에게 불필요한 불편을 주지 않는 범위에서 UI는 가능한 한 단순하게 구현한다.
* 기능 구현을 위해 필요하지 않은 버튼, 메뉴, 단계, 모달, 설정 항목, 별도 화면 등 UI 요소와 상호작용을 임의로 추가하지 않는다.
* 기존의 간단한 동작으로 충분하다면 더 복잡한 UI 구조로 바꾸지 않는다.
* 서로 연관된 기능과 정보는 가능한 한 같은 영역 또는 인접한 영역에 배치한다.
* 하나의 작업 흐름에 속하는 입력, 결과, 보조 기능을 불필요하게 서로 떨어진 위치에 배치하지 않는다.
* 사용자가 특정 기능을 수행하기 위해 화면의 여러 영역을 오가거나 관련 기능을 찾아다녀야 하는 구조를 피한다.
* 기능의 위치는 단순한 시각적 균형보다 사용 흐름과 기능적 연관성을 우선한다.
* 화면 구성은 기능 단위를 기준으로 위에서 아래로 읽었을 때 자연스럽게 이해될 수 있도록 한다.
* 관련 기능은 필요한 경우 같은 행에 배치할 수 있으나, 한 행에 여러 조작 요소를 과도하게 압축하지 않는다.
* `button`, 짧은 `input`, `select` 등 가로 폭이 작은 조작 요소는 서로 직접 연관된 하나의 기능 또는 작업 흐름에 속하고, 해당 요소들의 전체 배치 폭이 약 `360px`을 넘지 않는 경우 같은 행에 배치할 수 있다.
* 같은 행에 배치하는 조작 요소의 전체 폭이 약 `360px`을 넘거나, 긴 텍스트 입력처럼 충분한 가로 공간이 필요한 경우에는 별도의 행으로 분리한다.
* `textarea`와 같이 본질적으로 넓은 입력 영역이 필요한 요소는 다른 주요 조작 요소와 같은 행에 억지로 배치하지 않는다.
* 서로 관련 없는 기능은 각 요소의 폭이 작더라도 단순히 공간을 절약하기 위해 같은 행에 배치하지 않는다.
* 한 행에 여러 요소를 배치할 수 있다는 이유로 입력, 실행, 설정 등 서로 다른 작업 단계를 무리하게 한 줄에 몰아넣지 않는다.
* 화면을 작게 만드는 것보다 기능 간 관계와 각 조작 요소의 역할이 명확하게 이해되는 배치를 우선한다.
* 단순한 공간 확보를 목적으로 `<br>`을 반복해서 사용하지 않는다.
* 렌더러가 생성하는 사용자 문서 콘텐츠를 제외한 openNAMU 내부 UI에서는 기능이나 영역을 구분할 때 `<br>`보다 `<hr class="main_hr">` 사용을 우선한다.
* `<hr class="main_hr">`은 내부 화면의 기능 또는 영역 구분 용도로 사용하며, 단순히 문장 안에서 줄을 바꾸기 위한 용도로 사용하지 않는다.
* 기존 내부 화면에서 `<br>`을 새로 추가해야 할 경우 `<hr class="main_hr">`으로 목적을 달성할 수 있는지 먼저 확인한다.
* 렌더러 출력은 문서 문법과 사용자 콘텐츠의 표현을 우선하므로 위 `<br>` 및 `<hr class="main_hr">` 원칙의 적용 대상에서 제외한다.
* JavaScript 없이 구현할 수 있는 기능은 가능한 한 서버 렌더링, HTML, CSS만으로 구현한다.
* JavaScript는 사용자 편의나 기능상 명확한 이점이 있을 때만 추가한다. 단순한 화면 전환이나 서버에서 처리할 수 있는 동작을 위해 불필요하게 도입하지 않는다.
* JavaScript가 필요한 경우에도 해당 기능에 필요한 최소 범위로 제한하며, 단순한 기능을 위해 전역 상태나 대규모 프론트엔드 구조를 만들지 않는다.
* 새 사용자 표시 문자열은 기존 언어 시스템을 사용하며 View나 API에 특정 언어의 사용자 표시 문자열을 직접 하드코딩하지 않는다.
* 기존 번역 키를 재사용할 수 있다면 같은 의미의 새 번역 키를 만들지 않는다.
## API 원칙
* API의 외부 호출 진입점은 `Api_*` 함수로 구현한다.
* `Api_*` 함수는 보호된 데이터를 반환하거나 상태를 바꾸기 전에 스스로 권한을 검사한다.
* 현재 View가 이미 검사하더라도 API에서 모든 외부 입력값과 식별자를 검증한다.
* API 동작에 필요한 입력 정규화(trim, 형식 변환, 기본값 처리 등)는 View에 의존하지 않고 API 또는 공용 헬퍼에서 수행한다.
* 반환 map의 키와 Go 타입은 모든 호출자에서 일관되게 유지한다. 오류 또는 선택 값에 대해 View가 검증 없는 타입 단언을 하지 않도록 한다.
* API는 `ok`, `require auth`, `not exist`, 검증 오류 등 호출자가 후속 처리를 결정하는 데 필요한 상태를 명확히 구분해서 반환한다.
* 같은 종류의 오류는 기존 API의 오류 코드와 반환 형식을 재사용하며, 동일한 의미를 가진 새 오류 표현을 임의로 추가하지 않는다.
* 잘못된 입력이나 처리 실패를 임의의 기본값으로 조용히 대체하여 성공한 것처럼 처리하지 않는다.
* 오류를 복구할 명확한 기존 동작이 없다면 호출자가 판단할 수 있도록 실패를 명시적으로 전달한다.
* 읽기 API는 상태를 변경하지 않는다. 쓰기 API는 필요한 쓰기 작업 전체를 책임진다.
* 함께 성공하거나 실패해야 하는 DB 쓰기는 API가 소유하는 하나의 트랜잭션으로 묶는다.
* 트랜잭션 내부에서 새 DB 연결을 여는 API를 호출하지 않는다. 트랜잭션 안에서 데이터가 필요하면 현재 `tool.DB_runner`를 받는 작은 내부 헬퍼를 사용한다.
* 트랜잭션 내부에서 롤백할 수 없는 외부 부작용을 임의로 수행하지 않는다. 파일, 캐시, 외부 시스템 등 DB 트랜잭션으로 되돌릴 수 없는 작업이 필요한 경우 DB 작업과의 실행 순서와 실패 처리를 명시적으로 설계한다.
* 읽을 수 있는 문서 설정 목록과 쓸 수 있는 문서 설정 목록은 분리한다. `last_edit` 같은 내부 값은 읽기 허용 때문에 쓰기 허용이 되면 안 된다.
## 구현 원칙
* 새 함수, 헬퍼, 상수, 설정, 오류 코드 등을 추가하기 전에 저장소에 같은 목적의 기존 구현이 있는지 검색한다.
* 비슷한 구현이 이미 있다면 새 구현을 병렬로 만들기보다 기존 구현을 재사용하거나 필요한 최소 범위에서 확장한다.
* 동일한 규칙이나 상수 값을 여러 위치에 각각 정의하지 않는다.
* 새 외부 라이브러리를 추가하기 전에 Go 표준 라이브러리와 기존 의존성으로 구현할 수 있는지 먼저 확인한다.
* 작은 기능 하나를 위해 큰 라이브러리나 프레임워크를 추가하지 않는다.
* 새 런타임, 별도 서비스, Node.js/npm 등 추가 실행 환경을 요구하는 구조는 명시적인 필요가 없는 한 도입하지 않는다.
* 요청 시 바로 처리할 수 있는 작업을 위해 별도 작업 큐, 백그라운드 워커, 이벤트 시스템 등을 도입하지 않는다.
* 캐시, 비동기 처리, 백그라운드 작업은 실제 성능 또는 기능상 필요가 확인된 경우에만 추가한다.
* 가독성과 단순성을 희생하는 성능 최적화는 실제 병목이 확인된 경우에만 수행한다.
