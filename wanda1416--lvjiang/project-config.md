# AI Agent 协作规范

本文件适用于整个仓库。目录内若存在更具体的 `AGENTS.md`，则以更具体的规则为准。
发布细节以 [`packaging/readme.md`](packaging/readme.md) 为唯一完整操作手册；本文件规定
AI Agent 的授权边界、提交组织和执行门禁。

## 一、操作授权

- “检查”“分析”“评审”“给出方案/数量”是只读任务，不授权修改文件或历史。先报告
  结论，等待用户说“执行”后才能按已说明的方案落地。
- “修改”“实现”“编写”授权修改工作区，完成后不得自行提交、推送、合并分支或打标签。
- “提交”授权把本次任务范围内的变更整理成提交，但不自动授权推送。
- “推送”授权为当前任务创建必要提交并推送当前分支；若用户明确说“只推已有提交”，
  则不得夹带工作区变更。
- “准备发布 `X.Y.Z`”授权修改版本号、发布说明并完成验证；是否提交、推送仍按用户
  同一句话中的要求执行。它不授权合入 `master` 或打标签。
- “发布 `X.Y.Z`”授权执行本文和 `packaging/readme.md` 规定的完整标准发布流程，包括
  发布准备提交、进入 `master`、推送发布提交、创建并推送标签。若用户要求二次确认，
  必须在合入 `master` 和打标签之前停下。版本号、目标分支或发布基线不明确时不能猜测。
- “整理/合并提交”“rebase”只授权本地改写。改写已经推送的分支以及强制推送，必须
  得到明确授权；用户在已说明会改写远端历史的方案后说“执行”，视为对该方案的明确授权。
- 不得把当前任务之外的用户改动纳入提交，不得清理、还原或覆盖无法确认归属的改动。
- 多个 Agent 或工作副本并行时，先确认当前目录、分支、远端 tip 和工作区归属；用户指定
  在另一个目录操作时不得留在当前目录。不得用 reset、checkout 或整文件覆盖处理并行冲突。
- 用户真实姓名、账号、角色、设备信息、API key、`config/session` 内容和其他私人设定
  不得写入源码、测试、提交信息、公开文档或 `AGENTS.md`。用户提供的真实数据只可用于
  本地复现，提交前必须检查 staged diff 和待发布历史中没有残留。

## 二、需求理解与状态边界

### 2.1 以用户最后一次纠正为准

- 用户对术语、范围或目标的纠正会替换之前的错误解释。收到“不是 A，是 B”后，必须
  重新检查当前方案、文档和待执行操作，不能只在回复里换词却继续按 A 执行。
- 不确定的业务词应结合页面、数据流和现有代码确认。不得把“某版本以来的功能”误解为
  “依赖功能”，也不得把提交标题当成功能清单；版本盘点以基线到目标的最终差异为准。
- 需求包含两个相似概念时，先明确各自的所有者、生命周期和是否持久化，再设计信号和
  数据写回。不能因为控件相同就共用状态。

### 2.2 配置、编辑态与运行态分离

实现设置页、配置组和主页面联动时，至少区分以下状态：

1. **持久化配置**：定义可见项、初始值和初始顺序；
2. **编辑器状态**：当前正在编辑哪个对象，以及尚未保存的草稿；
3. **默认/活动选择**：主页面或运行入口默认使用哪个配置；
4. **临时运行状态**：本次会话中的排序、勾选、过滤和实际执行顺序。

- 切换编辑对象只改变编辑器上下文，不得顺带改变主页面默认/活动选择。
- 临时运行排序不得反写持久化的初始排序；保存配置也不得无条件覆盖用户已经调整的
  本次执行顺序。确需同步时，必须是需求中明确描述的单向动作。
- 程序化刷新控件时要阻断或守卫会写配置的信号，防止“为了展示而切换”触发持久化副作用。
- 删除或重命名配置可以修复已经不存在的默认引用，但不得以“保持一致”为由改变仍然
  有效的默认选择。
- 状态边界必须有回归测试，至少验证“切换编辑对象不改默认值”“运行态重排不改配置”
  以及重新加载时从持久化初始值正确构造运行态。

### 2.3 批量页面的固定语义

- 批量配置内层的排序和筛选负责**可见性与初始顺序**，属于配置组定义。
- 主页面外层的脚本/用户排序负责**本次实际执行顺序**，属于临时运行态。
- 批量配置窗口是纯配置组编辑器；仅仅切换正在编辑的组，不能改变主页面默认选中的组。
- 新建、重命名、删除配置组时，只处理名称和悬空引用所必需的变化，不把编辑器当前项
  当作新的默认组。

### 2.4 证据优先，禁止凭假设补复杂度

- 分析问题前先同步并检查用户指定的最新代码、最近相关变更、真实日志、截图和现有配置。
  不能拿旧工作区、过期文档或记忆中的实现解释当前现象。
- 明确区分已验证事实、代码推断和边界猜测。用户提供了实际数据时，优先用数据复现；
  声称算法存在反例、性能瓶颈或平台限制时，应给出可验证证据，而不是只说“理论上可能”。
- 先找根因和既有权威数据源，再决定增加字段、状态或抽象。不得为极端且不可操作的情况
  堆叠防御代码，也不得用新内置函数、新配置或新缓存掩盖已有能力可以解决的问题。
- 用户说“先分析/先给方案/先确认概念”时，先输出数据流、状态语义、影响范围和取舍；
  复杂需求未获确认前不进入实现。
- 用户否定前一方案或说“忘掉前面结论”后，必须回到事实重新推导，清理前一方案引入的
  假设，不能在旧方案上继续打补丁。

### 2.5 单一来源与运行快照

- 已有系统配置、领域模型或公共引擎是权威来源时，不得在 UI、工作流或业务类再维护一份
  平行常量。硬编码游戏事实应进入相应配置或机制登记，并由消费者共同读取。
- 稳定 ID/key 与展示 label/name 分离。持久化、文件名、引用和跨语言协议使用稳定 key；
  翻译文本只用于展示，不得作为用户名、文件名、枚举值或逻辑判断条件。
- 任务启动时冻结环境、参数、用户、脚本与执行顺序；执行中使用该内存快照，不重新读取
  用户可能正在修改的配置文件。需要动态变化的内容必须在需求中被明确声明。
- 保存对话框或配置编辑器只能合并自己拥有的字段。不得把打开窗口时读取的陈旧整份快照
  覆盖回磁盘，避免回滚其他进程、热键任务或页面刚写入的数据。
- 模拟、预览、假设和搜索使用派生副本，并保留到原始对象的稳定关联；不得原地改写原始
  数据。展示、应用或落盘时必须按需求明确选择原始对象还是派生结果。

### 2.6 抽象、复用与影响面

- 公共层只统一真正通用的原语和契约，例如 scan、click、输入、识别和任务调度能力；
  业务规则不能为了“统一”强塞进 DSL/core。
- 两段代码表面相似不等于语义相同。抽取公共实现前检查所有调用方、平台差异、返回值和
  失败语义；契约不同就保留专用适配器，避免污染其他调用方。
- 新业务优先复用公共引擎能力，不复制 DSL 已有实现；死代码应删除，不应为了搬迁而搬迁。
- 平台共性进入公共能力，平台差异留在后端或 capability。不能把 PC 的 ESC、窗口行为或
  后台输入假设套到 Android，也不能用当前环境变量代替实际执行目标来选择后端。
- 新增字段、识别状态或 UI 展示时，默认不得改动原有核心流程和页面流转。确需改变流程，
  必须在方案中列出旧路径、新路径和所有消费者。
- 重构后的能力应至少覆盖重构前行为；若顺带纠正旧错误，要把行为变化和纯重构分别说明、
  分别验证。

### 2.7 兼容、迁移与失败边界

- 不默认保留兼容。对于用户可自行重配、尚未正式发布或维护兼容会形成长期负担的 schema，
  优先一次性切换并在发布说明中给出手工调整方法，不堆叠永久兼容代码。
- 只有用户无法自行恢复、数据不可替代或需求明确要求时才编写迁移。迁移必须以明确版本号
  驱动、可重复执行、不会二次迁移，并作为独立可审计提交；禁止依靠某个字段“看起来存在”
  的启发式判断。
- `config/local` 是用户主动覆盖，优先级高于 system 属于预期行为。不得为了让系统修正
  “生效”而静默覆盖、删除或重写 local。
- 单个脚本、配置、OCR 字段或装备解析失败，应在所属层隔离并留下可行动日志，不得拖垮
  其他条目或阻止应用启动。识别层负责吞并预期识别失败；业务层自行决定是否要求严格值。
- 预期不允许的 UI 操作应通过禁用控件或明确提示拦截，而不是等用户点击后抛异常。
- 不做无收益的过度防御；只处理有真实路径、合理概率或明确数据损失风险的故障。

### 2.8 UI 与交互一致性

- 相同层级和用途的按钮、列表、对话框与保存/撤销行为保持一致；标题不要在对话框内容区
  再重复一遍，也不要把实现 key、文件路径或内部术语暴露给普通用户。
- 输入框和下拉框必须完整展示常用最长内容，宽度要计算箭头、边距和控件装饰，不能只按
  文本宽度；空间不足时优先合理换行、滚动或布局重排，不随意省略用户名和关键状态。
- 禁用与隐藏含义不同：功能存在但当前不可用时应禁用并提供原因；确实不适用于当前环境
  或当前数据时才隐藏。
- 后台任务弹出的提示不得阻断主界面的停止/暂停等安全操作。局部状态变化只刷新相关控件，
  不得无理由触发全页面、全仓储或全配置重载。
- 删除、回收、覆盖等高风险 UI 默认采用保守范围，明确展示当前筛选条件和受影响对象并
  二次确认；不能把模拟数据、穿戴数据或被其他方案引用的数据悄悄纳入批量删除。

### 2.9 文档与可观测性

- 复杂新功能先补 `docs/20-requirements` 的需求与边界，涉及公共结构时同步架构文档，完成
  后更新用户指南。不能让代码、需求、方案和用户文档描述四套不同流程。
- 文档写当前已经实现和验证的事实。规划能力、未开放内部模型和待完成工作必须明确标注，
  不得写成用户已经可用；过期结论应直接修正，不能因为曾经发布过就继续保留错误描述。
- 自动化流程的重要状态、决策原因和状态变迁应在实时进度、结构化历史和适当级别日志中
  一致可追踪。日志应给出可行动信息，不打印超长原始 JSON，也不重复输出已有报告全文。
- `warning`/`error` 只用于真正异常或需要用户处理的状态。可选弹窗未出现、允许为空的 OCR
  等正常分支不能制造告警噪声；实际数据矛盾、可能误操作或状态机失配必须明确报错。

## 三、提交基本原则

提交以“可独立理解、可独立审阅、可安全回退”为目标，而不是追求最少数量。

### 3.1 应当合并的内容

- 同一功能从实现到稳定之间的零散 `fix`、遗漏导入、类型修正和测试补充，合并回该
  功能提交；尚未发布的开发期缺陷不保留为独立修复提交。
- 与某项代码变更强绑定的测试、少量配置、JSON/YAML、翻译键和用户文档，随对应功能
  一起提交，避免只改一个字段的碎片提交。
- 对同一职责、同一模块进行的连续机械调整，且中间状态没有独立审阅或回退价值时，
  可以合并。
- 纯粹修正前一个提交的拼写、格式、lint、mypy 或测试失败，应使用 `fixup!` 后
  autosquash，最终历史不保留修补噪声。

### 3.2 必须保持独立的内容

- 相互独立、可分别回退的用户功能或问题修复。
- 不兼容迁移、数据格式变化、DSL/公共接口变化和安全相关改动。
- 发布说明与版本号准备提交；该提交固定使用
  `chore(release): prepare vX.Y.Z`，不得揉进功能提交。
- 大型重构不得仅因都标为 `refactor` 就合成一个提交。重构应按层次或职责拆分，例如
  core 模型、配置边界、UI 组件、后台任务、目录迁移分别成组。
- 性能优化若有独立测量、行为边界或回退价值，应与一般重构分开。
- 仅在上一正式版本中已经存在的用户可见缺陷，才保留独立 `fix` 语义并进入发布说明；
  本开发周期引入又修正的问题合并回引入提交。

### 3.3 审计粒度

- 一个提交只回答一个主要问题。提交说明应能解释“为什么需要这组变化”，而不只是列文件。
- 重构提交应尽量限制在一个子系统或一个依赖方向；跨多个子系统时，按可编译、可测试的
  依赖顺序拆分。
- 不规定固定的提交数量。若合并后需要同时理解多个无关领域才能审阅，说明合并过大；
  若连续提交只有一个 JSON/YAML 字段、一个测试遗漏或前一提交的修补，说明拆分过细。
