# Agent Instructions for OPCloud Models

These instructions apply to the entire repository. Follow them whenever an agent creates, edits, reviews, or validates an OPCloud `.opcl` or compatible `.json` model.

## Objective

Produce models that:

1. import successfully through `opcloud-model-io.user.js`;
2. render correctly in OPCloud Sandbox;
3. express valid Object-Process Methodology (OPM) semantics;
4. generate OPL sentences that accurately describe the diagram.

Use [`examples/Two-Dish-Dinner-Corrected.opcl`](./examples/Two-Dish-Dinner-Corrected.opcl) as the canonical schema template. Preserve fields that are not explicitly understood instead of deleting or renaming them.

## Model Generation Contract

When a user asks an agent to generate an OPCloud model, the agent must deliver a complete, directly importable file—not pseudocode, a partial object, an OPL-only description, or a conceptual outline.

- If the user asks for `.opcl`, write UTF-8 JSON with the `.opcl` extension.
- If the user asks for JSON, write the same valid OPCloud serialization with the `.json` extension.
- `.opcl` is JSON data; do not add JavaScript, Markdown fences, comments, or trailing commas to the file.
- Use the exact target path and filename requested by the user. Otherwise, choose a descriptive filename.
- Base new files on the canonical exported example so all required OPCloud fields are retained.
- Generate OPL indirectly through correct OPD/OPCL semantics. OPL sentences are generated by OPCloud and are not manually stored as a substitute for the model.
- Deliver the created file and summarize its objects, processes, states, and relations.
- State which validation levels were completed: JSON parsing, reference validation, OPCloud import/rendering, and OPL review.

A generated file must contain at least these top-level fields:

```json
{
  "name": "Model Name",
  "description": "Model purpose",
  "archiveMode": {
    "archiveMode": false,
    "date": "",
    "user": ""
  },
  "permissions": null,
  "currentOpd": {},
  "logicalElements": [],
  "opds": [],
  "stereotypes": []
}
```

The abbreviated objects above illustrate required top-level keys only. For a real deliverable, populate them using complete structures cloned from a valid export.

## Modeling Rules

### Things

- Name objects with nouns, such as `Home Cook`, `Soup Pot`, or `Vegetable Soup`.
- Name processes with gerunds or action nouns, such as `Vegetable Soup Cooking` or `Ingredient Preparing`.
- Use an object state only when the same object changes over time, such as `not ready` to `ready`.
- Do not model two unrelated entities as states of one object.
- Keep peer processes at the same visual level and do not add Invocation links between them.

### Essence and affiliation

Use the numeric values expected by OPCloud:

| Field | Value | Meaning |
|---|---:|---|
| `essence` | `0` | Physical |
| `essence` | `1` | Informatical |
| `affiliation` | `0` | Systemic |
| `affiliation` | `1` | Environmental |

An agent is normally a physical environmental object. Tools, inputs, outputs, and the modeled system are normally systemic unless the scenario requires otherwise.

### Link types

Use `OpmProceduralRelation` for procedural links and `OpmFundamentalRelation` for structural links.

| `linkType` | Relation | Direction | Expected OPL |
|---:|---|---|---|
| `0` | Agent | agent object → process | `Agent handles Process.` |
| `1` | Instrument | instrument object → process | `Process requires Instrument.` |
| `2` | Consumption | consumed object/state → process | `Process consumes Object.` |
| `3` | Result | process → generated object/state | `Process yields Object.` |
| `4` | Effect | object ↔ process | `Process affects Object.` |
| `5` | Invocation | invoking process → invoked process | `Process invokes Process.` |
| `11` | Aggregation | whole → part | `Whole consists of Part.` |
| `12` | Exhibition | exhibitor → feature/process | `Exhibitor exhibits Feature.` |
| `13` | Generalization | specialized → general | generalization sentence |
| `14` | Instantiation | instance → class | instantiation sentence |

Rules:

- Use Agent only for a human or otherwise agentive environmental object.
- Use Instrument when the object is required but not transformed.
- Use Consumption when the input ceases to exist in its modeled form.
- Use Result only from a process to the object or state that the process actually creates.
- Do not connect two peer processes with Invocation merely to indicate visual order.
- For a composite object, use Aggregation from the whole to each part. Do not claim that each contributing process independently creates the complete aggregate.

### State changes

For an object changing from state A to state B:

1. create both `OpmLogicalState` elements;
2. set each state visual's `fatherObjectId` to the parent object visual ID;
3. list both state visual IDs in the parent object's `children` array;
4. add a Consumption link from state A to the process;
5. add a Result link from the process to state B.

This should generate:

```text
Process changes Object from A to B.
```
