# CLAUDE.md: steps Pipeline Runner

Trust these instructions. Only search the codebase if something here is missing or turns out to be wrong — this file is validated, not guessed.

## What this repo is

**steps** is a Go CLI that executes Concourse-style YAML pipelines (`resource_types`/`resources`/`jobs`), with an LLM `agent` step type built in alongside conventional `get`/`task`/`put` steps. Resources are discovered/fetched via templated shell commands (or MCP); `agent` steps call an LLM with tool calling. All state is cached in SQLite (WAL mode) via content-addressed (merkle) hashing, so unchanged steps are skipped on rerun.

- **The state database is bounded, and both bounds are pipeline settings.** `defaults.version_history:` caps recorded resource versions per resource; `defaults.run_history:` caps runs per job, and reaping a run takes its events, per-step records, agent usage, placements, questions and inputs with it (`internal/store/sqlite/retention.go`, called at the end of every build from `pipeline.RunJob`). Zero means no limit for both, per the convention in [docs/attempts-timeout.md](docs/attempts-timeout.md#zero-means-no-limit). `internal/store/sqlite/footprint_test.go` MEASURES the result with sqlite's `dbstat` — a change that grows what a build costs on disk fails there, which is the point.
- **History is bounded by recency; the CACHE is bounded by count, never by age.** `nodes` and `job_runs` are the merkle/chain caches, capped as a multiple of `run_history:` and evicted newest-by-`rowid`. Age is the wrong question for them and was a real bug: a fully-cached poll records no new node, never reaches `recordChainSucceeded`, and publishes its skip events with an EMPTY hash (`reportChainSkipped`), so nothing about a cache HIT refreshes any timestamp — a working pipeline's entries just looked older every poll until an age-based floor swept past them, and the faster it polled the sooner it lost the cache. A count cap cannot do that: a fully-cached pipeline creates no new entries, so nothing is ever evicted.
- **Stored timestamps use `sortableNano`, not `time.RFC3339Nano`.** These columns are ordered and compared as TEXT, and RFC3339Nano TRIMS trailing zeros — so `…:00.5Z` sorts after `…:00.51Z`, and a whole second sorts after every fraction inside it. Retention DELETES by that order, which made it able to reap the newer of two runs in one second. Any new stored timestamp uses the fixed-width layout. That is sqlite's rule; the Postgres driver stores `timestamptz` (truncated to the microsecond it keeps, read back `.UTC()`) and breaks ties with an identity column, which is its answer to both halves of the same problem.
- **The daemon HOLDS pipelines; `steps pipeline set` uploads them.** `steps web` takes no pipeline arguments and starts empty: a pipeline arrives over HTTP (`PUT /api/pipelines/<name>`, `internal/web/api.go`) and by nothing else, which is what makes vars per-set rather than process-wide, makes a pipeline's identity a NAME somebody chose rather than a filename, and makes a change happen because somebody asked rather than because a file moved. There is no file watcher and no `--once` (both deleted with #104). The set path is `internal/cli/daemon.go` — the half that chooses a store driver and a workspace provider, implementing `web.Manager`, which `internal/web` deliberately does not do. Three properties are load-bearing. **Validation happens on the machine that will RUN it** (`daemon.accept`: parse, `fileProblems`, `CheckEnvironment`, workspace) and the refusal travels back over HTTP to the terminal that asked — that is the whole reason the transport is not a database row, which would need an ack protocol of its own. **Includes travel as a bundle**: a `run_file:` is pipeline-relative and a daemon has no sibling filesystem, so `set` sends `{source, includes}` and the daemon resolves through `config.Bundle`, which is CLOSED on purpose — an include it was not sent must fail rather than read the daemon's own disk. **The workspace provider is leased** (`internal/web/providers.go`): a set may replace it, and `Close` removes the tree it created, so a run keeps the provider it started with and the old one is closed only once the runs holding it finish. `steps run`/`test`/`validate`/`plan` still take a file path — they are the local commands, and a local command has a file.
