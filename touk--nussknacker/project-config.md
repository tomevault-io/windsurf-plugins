# AGENTS.md — Nussknacker Designer Submodules

React 18 / TypeScript 5.9 / Webpack 5 frontend submodules for the Nussknacker designer.
This is an **npm workspaces monorepo** (`@nu/submodules`) with one workspace package `@nu/components`
loaded at runtime via **Webpack Module Federation** from the host app (`designer/client`).

## Architecture

-   **Host app**: `designer/client/` — exposes config, HttpService, Auth, Icon, etc.
-   **This repo** (`designer/submodules/`): remote that exposes `./list` and `./scenarios` views
-   Runtime integration via Module Federation (`federation.config.json`, name: `nu_components`)
-   Remote type declarations are generated by `make-federated-types` into `types/@remote/`
-   Shared webpack configs live in `configs/webpack/`

## Build & Development

```bash
npm run build              # Production build (all workspaces)
npm run start              # Dev server at localhost:5001 (Module Federation remote)
npm run start:core-dev     # Dev with local host app at localhost:3000
npm run start:core-staging # Dev against staging at staging.nussknacker.io
npm run lint               # syncpack-lint + ESLint --fix
npm run make-types         # Generate federated type declarations
npm run test               # Run tests across all workspaces
```

The dev server for `@nu/components` runs on **port 5001**. It expects the host app
(`designer/client`) to be running at the URL specified by `NU_FE_CORE_URL` (default from `.env`).

### Docker

```bash
npm run docker-build       # Build nginx-based production image
npm run docker-run         # Run container at localhost:13011
```

## Testing

Currently no Jest/test config in submodules. Tests run via workspace delegation:

```bash
npm run test                                   # Delegates to all workspaces
```

If tests are added, follow the same patterns as `designer/client/`:

```bash
npx jest --testPathPattern="ComponentName"     # Run single test file by name
npx jest path/to/test.ts                       # Run specific test file
npx jest --testNamePattern="should render"     # Match test description
npx jest --watch                               # Watch mode
```

## Code Style

### Formatting (Prettier)

-   **4 spaces** indentation, **140 char** line width
-   **Semicolons** required, **trailing commas** everywhere (`"all"`)
-   Double quotes (Prettier default)
-   LF line endings, final newline required (root `.editorconfig`)

Run `npx prettier --write <file>` to format. Enforced via lint-staged on commit.

### Imports (ESLint `import/order` — warn level)

Three groups separated by blank lines, alphabetically sorted within each group:

```typescript
// 1. Builtin (node)
import path from "path";

// 2. External/third-party packages
import { css } from "@emotion/css";
import type { Theme } from "@mui/material";
import React, { useMemo } from "react";
import { useTranslation } from "react-i18next";

// 3. Internal (relative: parent, sibling, index)
import { SomeComponent } from "../components/SomeComponent";
import type { Settings } from "./types";
```

Critical import rules:

-   **Type-only imports must use `import type { X }`** — `@typescript-eslint/consistent-type-imports` (warn)
-   **Wildcard imports (`import * as X`) are banned** — use named imports (warn)
-   Sorting is case-insensitive ascending

> **Note:** These rules are at `warn` level (vs `error` in `designer/client`). Follow them strictly anyway.

### TypeScript Conventions

-   **`type` preferred** for data shapes and unions; `interface` acceptable for component props
-   TypeScript 5.9 — checking only, **Babel transpiles** (`isolatedModules: true`)
-   `target: es5`, `module: commonjs` (root), `module: esnext` (components package)
-   `@typescript-eslint/no-inferrable-types` is **off** — explicit types on trivially-inferred values are allowed
-   CSS modules supported via `typescript-plugin-css-modules`
-   Path aliases: `*` resolves to `["*", "types/@remote/*", "types/*"]`
-   `skipLibCheck: true`, `isolatedModules: true`

### Naming Conventions

| Element           | Convention                             | Example                   |
| ----------------- | -------------------------------------- | ------------------------- |
| React components  | PascalCase                             | `ScenarioCard.tsx`        |
| Hooks             | camelCase with `use` prefix            | `useSettings.ts`          |
| Utilities/helpers | camelCase                              | `navigation.tsx`          |
| Styled components | PascalCase                             | `StyledPanel.tsx`         |
| Test files        | `{name}.test.tsx` or `{name}-test.tsx` | `utils-test.ts`           |
| Directories       | camelCase                              | `scenarios/`, `settings/` |
| Federated entries | camelCase                              | `componentsNkView.tsx`    |

### Internationalization (i18n)

The `i18next` plugin is available but **not enforced as error** in submodules (unlike client).
Still, use `react-i18next` `useTranslation()` for all user-facing strings — consistency with the host.
