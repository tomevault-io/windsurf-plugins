# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

suiteDFIR is a **single-user desktop application** that runs entirely on the investigator's workstation. Forensic extraction, parsing, and case data stay local — the backend binds to loopback only and the only outbound network calls are for map tiles and geocoding (Google/Carto/OSM/Nominatim). There is no multi-tenancy, no auth layer, no remote API, and no shared state to coordinate; do not add features (sessions, user IDs, RBAC, server-side rate limiting, etc.) that assume otherwise.

## Common Commands

Install everything (root, frontend, electron) — backend deps go through pip separately:
```bash
corepack enable                   # once per machine; see "Yarn version" below
yarn install:all
cd backend && python3 -m venv venv && source venv/bin/activate && pip install -r requirements.txt
```

Run the full app in dev (Vite on :3000 + Electron spawning the venv backend on :8000 with hot reload):
```bash
yarn dev:electron
```

Run pieces in isolation:
```bash
yarn dev                          # Vite only (frontend at :3000, expects backend at :8000)
yarn electron                     # Electron only (will spawn backend itself)
cd backend && source venv/bin/activate && python -m src.main --port 8000   # backend only, dev style
```

Build:
```bash
yarn build:backend                # PyInstaller bundle → backend/dist/suiteDFIR Backend/
yarn build:frontend               # Vite static build → frontend/dist/
yarn build:mac | build:linux | build:win   # full platform bundle (calls scripts/build-*.sh)
```

Tests (pytest, async-aware):
```bash
cd backend && source venv/bin/activate
pytest                            # whole suite
pytest tests/api/test_cases_api.py
pytest tests/services/test_case_manager.py::test_create_case
pytest -k "encrypt"
```

Frontend lint: `cd frontend && yarn lint`. No frontend tests exist.

## Yarn version

Yarn is **pinned to a single version** via `packageManager` in the root `package.json`, supplied by corepack. Do not remove that field, and do not commit a lockfile generated by a different Yarn major.

Yarn 4 (Berry) lockfiles start with `__metadata: version: 10`; Yarn 1 (Classic) writes an incompatible `# yarn lockfile v1`. Yarn 1 **ignores** `packageManager`, so a contributor with a globally npm-installed `yarn` rewrites all lockfiles wholesale on their first install. If a lockfile diff is thousands of lines for a trivial dependency change, check `head -6 yarn.lock` before anything else.

There are two install roots — the workspace root (with `frontend` as its only workspace) and `electron/`, which installs separately and has no lockfile-sharing relationship to the root. Both are covered by one pin: corepack cascades `packageManager` from the nearest ancestor `package.json`, and Yarn cascades `.yarnrc.yml` the same way, so the root `.yarnrc.yml` (`nodeLinker: node-modules`) also governs `electron/`. Without it, Yarn 4 would default to PnP there and break the Electron build.

The root package and the `frontend` workspace must not share a name — Yarn 4 rejects duplicate workspace names, which is why `frontend/package.json` is `suitedfir-frontend` while the root is `suitedfir`.

CI must run `corepack enable` **before** `actions/setup-node`, because setup-node's `cache: yarn` shells out to `yarn --version` to locate the cache directory, and GitHub runners ship Yarn 1 globally.

### Install scripts are off by default

Yarn 4 defaults `enableScripts` to **false** — dependency `postinstall` hooks do not run. This is a supply-chain guard and is deliberately left at the default. Do **not** flip it to `true` globally to fix a broken install; that re-enables lifecycle scripts for every transitive package.

Instead, opt in the specific package via `dependenciesMeta.<pkg>.built: true`, which overrides the global default for that package only. Exactly one package is opted in:

- `electron/package.json` → `electron`. Its postinstall downloads the ~195MB platform binary; without it `node_modules/electron/dist` is empty and the app cannot launch.

Install prints `YN0004: <pkg> lists build scripts, but all build scripts have been disabled` for `esbuild` and `msw` at the root. **This is expected — neither needs its script, and the warning is not a problem to fix:**
- `esbuild` ships its real binary as the `@esbuild/<platform>` optional dependency (a plain package fetch). Its `install.js` only hard-links a shim over the JS wrapper, and that step self-skips under Yarn anyway (`isYarn()` check), so the script is a no-op here. The only thing lost is its startup version-consistency check, which would surface at runtime instead.
- `msw`'s postinstall returns immediately unless the consuming `package.json` declares an `msw.workerDirectory` key. This project doesn't (no browser service worker is used), so it does nothing.

Both were verified: with all root build scripts disabled, `yarn --cwd frontend run test:coverage` (176 tests) and `yarn --cwd frontend run build` pass.

A **new** `YN0004` for a different package means a dependency may genuinely need an entry. Read its install script before adding one — don't reflexively flip `enableScripts`.
